# Decisions log

Format: **what** · *why* · alternatives rejected. Dates are approximate (the project ran from September to October 2026). Newest decisions last.

| # | Decision | Why / what was rejected |
|---|---|---|
| D01 | One JSON file per day plus derived files | Cheap re-runs and small diffs. Rejected: one large `hydro_data.json` (frozen legacy copy was removed). |
| D02 | `null` ≠ `0`; a new `null` never overwrites a value, a new value always does | Safe merging of partially published days; wrong data are repaired by re-running. |
| D03 | Store everything on **Greek local time**; shift ISP and MCP by +1 h | One clock for the page; verified on 288 days (median correlation 0.984). Rejected: keep each source on its native clock. |
| D04 | Lookback of 4 days on every run | Late ADMIE files heal on the next run without manual action. |
| D05 | Volume = fill % × capacity from Professor Stefanakos's PDF; keep ADMIE's official total separately | Official total is volume-weighted and our rebuild is 0.98 pp lower; both are shown. |
| D06 | ENTSO-E weekly value = mean of end-of-day readings (Monday+1 … +7) | Best fit by far; an earlier "end of week" conclusion (from summer data only) was wrong. |
| D07 | Cascade model (sum of downstream plant factors) fitted by NNLS; report energy per **river**, not per dam | Per-dam factors are not identifiable (synthetic test). A single factor was 4.5× worse. |
| D08 | Two energy numbers: "ENTSO-E equivalent" (primary, calibrated) and "physical estimate" (gross head); Aoos shown separately | Owner agreed; they answer different questions and the page says so. |
| D09 | Gross head (not net) in the physical estimate | Data prefer it (κ = 1.005 vs 1.127). |
| D10 | Pigai Aoou is excluded from the ENTSO-E equivalent | Data show 0–200 MWh/hm³, not ≈ 1,795. Rejected: an unofficial document's claim. Revisit when more autumn data or ADMIE methodology is available. |
| D11 | 0.00 % readings on large dams are interpolated in calculations only | Ilarionas read 0.00 % for 19–25 July (63 hm³). Raw files stay untouched; the banner explains. |
| D12 | The water balance is called **apparent inflow** | It includes unmeasured withdrawals and losses; it must not be read as a flow measurement. |
| D13 | Sfikia and Asomata form one group in the balance | The pump cancels algebraically; avoids using the uncertain pump estimate. Proven and tested. |
| D14 | Ilarionas stays a separate group, with a caveat | Owner: the unit is faulty and must not be merged with Polyfyto. The split is unreliable while it does not turbine; the sum and the river total are unaffected. |
| D15 | Pumping per plant = SCADA total split by hourly ISP share (day share as fallback), always labelled *estimate* | SCADA/ENTSO-E have no per-plant pumping. DAM/intraday prices are deliberately **not** mixed in (owner: ISP vs SCADA is enough). |
| D16 | "Visible hydro" = TOTAL HYDRO + RESMV small hydro + Aulaki; RESMV flagged as an uncertified estimate | All small hydro (RESMV + PPC small + Aulaki) are ≈ 12 % of visible generation; RESMV alone reaches 21 % in April. |
| D17 | Kastraki > 100 % is normal and not flagged; a dedicated Kastraki tab tracks it | Owner knowledge; will matter when Amfilochia starts. |
| D18 | No pipeline changes for daylight-saving handling before 26 Oct 2026 | We have one real sample (29–30 March) and the effect is recoverable by re-running the day. |
| D19 | Recalibrate only on evidence (two weeks > 10 GWh out of sample) or in December | Factors moved ≤ 0.3 % when week 41 was added. |
| D20 | The page has no external libraries (SVG charts, vanilla JS) | Fully testable offline. To be revisited together with the shared look of all dashboards (Chart.js tooltips were proposed). |
| D21 | Scope: this repository is handled in its own threads; the other dashboards and the shared shell are separate work | Keeps context clean; everything needed to continue is in `docs/`. |
| D22 | `stored_energy.json` and the unused legacy files were retired | The page computes weekly/daily energy itself; fewer files to keep consistent. |
| D23 | Look and feel follows the other dashboards: dark slate base, breadcrumb to the hub, title, Last/Next Update, loading overlay, footer. The **accent colour is per dashboard**: BESS emerald, Gas-Power blue, Flows cyan, **BigHydro violet** (`--acc`, one CSS variable) | The house style is a shared base with one accent per site; violet keeps the four hub cards apart. Rejected: the previous light theme with automatic dark mode. |
| D24 | **English by default** with a Greek toggle; the preference is stored under the shared key `kp_lang` (all dashboards share one origin and can adopt it); the old key `bh_lang` is still read | Matches the other dashboards; a visitor's choice can follow them across the hub. |
| D25 | Charts stay hand-written SVG; **hover/touch tooltips with a crosshair** were added (no library) | Chart.js could not be checked visually in the test environment, while SVG was verified chart by chart; the user benefit (tooltips) is the same. Supersedes part of D20; revisit with the shared-shell work. |
| D26 | The banner and the "Complete/Partial data" badge consider only the sources the page uses: reservoir, SCADA, ISP, RESMV. MCP (price) is left out | Prices are not shown anywhere on this page. |
| D27 | "Next Update" is computed from the run times listed in `RUN_TIMES` in `index.html` (07:15, 09:15, 10:15 Athens) | Must be edited if the scheduler changes (for example a 13:30 safety run). |
| D28 | The footer repeats the owner's signature used on the other dashboards, plus data sources, a disclaimer and a link to this repository | Consistency with the hub; the disclaimer matters here (RESMV uncertified, estimates). |

| D67 | **Days of cover** is a section of the Stored energy tab: a table of named rate scenarios (current 30 days, average so far, highest month so far, largest single day), never one number, with a column for the **usual stock of the week** (median 2018–2025) so the reader sees more or fewer days than usual | A single number of days would be read as a forecast; the usual-stock column answers "more or fewer days than normal". |

| D70 | A **trend line** gives the stock change of the last 7 days, the equivalent inflow (generation of the same 7 days + stock change, a lower bound) and an "if this continued" duration labelled as an extension | The owner wanted generation and stock change to reveal what is arriving without waiting for the percentage to rise. |

| D73 | Below **1 GWh a day** the page says that **inflow cannot be told from zero** and shows the fall only; above it, the figure carries "± about 1" | The estimate is the difference of two numbers of 12–15 GWh a day; a few per cent of scale uncertainty is ≈ 1 GWh. | D75 | Before any backfill of ADMIE history there is a **read-only diagnose** (manual workflow, `contents: read`) that always ends green; a real backfill, if the data exist, must write to a **separate** file and not to `data/days/` | The existing `--only=reservoir START END` backfill writes day files and would mix past years into the 2026 series, the index and every derived file. |
| D76 | The ADMIE diagnose **measures what the API accepts before scanning** (two addresses × windows of 1–366 days around a known-good date) instead of assuming it, and treats an empty list for a long window as "not supported", never as "no history" | The first version assumed whole-year queries; the real API answered 200 with an empty list for every year including 2026 (where files certainly exist), so all zeros said nothing about the history. |
| D77 | The ADMIE history is back-filled, **if at all, into a separate file** (and per run of a few years), only after the formats diagnose has shown the labels of the old files and how duplicates should be chosen; the 2026 series in `data/days/` is never mixed with it | The diagnose showed that old reservoir files match only 10–11 of 14 reservoirs, old SCADA files lack the TOTAL rows, and some days have duplicate files; a backfill written before knowing this would silently produce a wrong baseline. |
| D78 | The historical parsers **reuse the pipeline's own parsers** after **renaming the labels of old files** in memory (reservoir: STRATOS1, POURNARI1, POURNARI2; SCADA: ΣΥΝΟΛΟ ΥΔΡΟΗΛΕΚΤΡΙΚΩΝ, ΑΝΤΛΗΣΗ); `update_hydro.py` stays untouched until after 26 Oct and the mapping is recorded in each year's file | Same semantics as the live series, no change to the running pipeline; the formats diagnose showed renamed labels, not missing data. |
| D79 | When a day has several versions of a file, **all are downloaded and compared**, the **latest** (publication time, then `_NN`) is kept and every difference goes to `Quality.Conflicts`; records pointing to the same path count once | Whether the versions differ is unknown (7 reservoir days in 2018); the choice is made visible instead of silent. |
| D80 | Missing is **null, never zero**; a day whose SCADA row lacks an hour gets null instead of a partial sum; **DST days** (23 or 25 hours) are flagged; failed downloads are listed and retried by the next run | A false zero or a partial sum would silently bias the baseline. |
| D81 | The backfill is run **first on a few days**, then in groups of 2–3 years, is resumable, never writes to `data/days/`, and shares the daily job's concurrency group | ≈ 15 minutes a year; a first real run on unseen old files must be small. |
| D82 | The full historical runs are done **in two runs of five years** (≈ 8 minutes a year, measured), **in the daytime** and **not on 24–26 Oct**, because the backfill shares the concurrency group of the daily job and a long run would queue the daily run on the day of the clock change | A queued daily run on 25–26 Oct would blur the one event we want to observe cleanly. |
| D83 | Among several versions of a day's file the backfill keeps the **most complete** (most values), then the latest; a version without any value is recorded as an `empty_version` conflict. **Supersedes the "latest" rule of D79** | A later version may be empty (24 Apr 2018); the first rule would have discarded real data. |
| D84 | **False zeros are removed:** a day with ≥ 10 reservoirs at exactly 0.0 % (or an official total of 0) is invalid; a reservoir at exactly 0.0 % between neighbours (≤ 3 days) above 5 % becomes null and is listed in `Quality.ZeroGlitches` | The ADMIE files contain zero-filled days (19–22 Mar 2020) and isolated zeros; left in, they would put 1,300 GWh of error into a week. | D85 | The yearly files are written with `allow_nan=False`, empty cells are null, and a run **without `--refresh` re-applies the cleaning to stored data** (it re-asks only days with no stored value and no invalid-file mark) | The first files contained `NaN`, which a browser cannot parse; old files can be repaired without downloading the decade again. |
| D86 | The history is **validated against the independent ENTSO-E series before it is used**: stock rebuilt from the ADMIE fill history with 2026-only factors, RMS 0.4–1.9 % of the stock in every year 2018–2025 | It shows that the parsers, the reference capacities and the factors are consistent over ten years, and it found the zero-filled days. |
| D87 | A day with **no reservoir value is invalid together with its "official total"** (a stale carry-over or a misdated file); the stored total of such days is dropped by the next run without refresh | The total is no evidence when nothing else in the file is: it repeated the previous day's value on 14–15 Dec 2020 and 6 Apr 2021, and equalled the 2018 value on 25 Apr 2017. |
| D88 | The **hourly pumping profile is not stored in the history** (2016–2025); the history keeps daily pumping only, and the hourly pumping series exists for 2026 alone. *Owner's decision, 20 Oct 2026* | It was offered as a way to test whether pumping moved from the night to the solar hours; the owner preferred to leave it. | D89 | Page tests that compare a **displayed whole number** with a value recomputed from the raw files **allow the precision of the stored value (0.25 GWh)**, not exact equality of two roundings | A CI failure on 20 Oct 2026 (card 2 of the previous-years panel: shown −135, exact −134.46) was a double rounding that appeared with the data of week 42; the test had been correct to notice it, but exact equality of rounded numbers fails at every .5 boundary, so it would fail again at random. |
| D90 | The cause of K04 is a **daily-total column read as a quarter-hour on a 23-hour day**, carried into H01 of the next day (proved on the stored 30 Mar data). The **fix for K04 and K05 is not deployed before 26 Oct**: 25 Oct stays an unmodified observation of what the pipeline does on a 25-hour day, which tests the predictions of DOMAIN_NOTES §9; the fix is then deployed (design in DOMAIN_NOTES §9) and 30 Mar and 25–26 Oct are re-run | The mechanism is known from the real files of past years, so waiting costs only two days of ISP-based quantities that are re-computable (the files stay on ADMIE); deploying a change to the daily parsers in the days before the event would give 25 Oct two possible explanations. |
| D91 | The clock-change fix is **integrated only after the real file of 25 Oct 2026 has been compared with the prediction** (the 24 SCADA columns are the first 24 chronological hours; the 25th hour is `total − sum`; H01 of 26 Oct is the 25th ISP hour).
